# 2026-11-01 报表状态与需求批量发布

## 证据与范围

生产基准 cd306f64、schema0099。03:43–03:58 北京时间附近的15分钟日志中，publish_state 累计约159秒；该值是多个 Worker 的阶段耗时之和，不是用户等待159秒，也不能与父阶段相加。代码对每个账户日期执行 session.get、状态更新、需求 SELECT FOR UPDATE 和 flush，形成逐桶往返。

本轮只改报表发布状态及需求确认的批量执行，并新增 publish_projection 阶段计时，区分同步发布与查询投影重建成本。无数据库迁移、持久化合同、平台额度、Worker并发、功能开关或云资源调整。

## 实现与正确性

- 沿用现有账户事务锁和 observed_at 水位过滤，仅处理实际可写桶。按500桶预读现有状态、更新并 flush，整个业务事务仍原子提交。
- 任务只读取一次并验证租户；每桶独立增加 publication_version。需求确认传递账户/日期到版本的映射，SQL 在 FOR UPDATE 前按实际二元组过滤，不取账户与日期集合的笛卡尔积。
- 执行代数、owner_epoch、冻结 requested_after、frozen_revision、新请求后继及已发布幂等规则保持；余额和目录继续复用原标量版本语义。
- 500是数据库语句批量大小，不是减少待处理账户数、降低Worker并发或每轮只同步500桶。超过500自动继续下一批，所有桶仍在同一事务。

## 验证

真实PostgreSQL/Redis定向测试：发布、水位、需求及新批量保护63项；大批量事实、余额、查询投影和阶段诊断52项，均通过（两组有1项重复）。Ruff/格式及三个生产模块mypy通过。

同一600个可写桶、2个受保护交叉桶样本：原版客户端数据库执行调用1915次，修改后13批，减少99.3%。计数包括状态和需求相关 execute/executemany；批量内仍可能执行多条数据库语句，不能解释成服务器仅执行13条SQL，也不能解释成整体系统快147倍。原版回归按预期失败，修改后通过。

样本同时核对600桶全部确认、不同既有版本分别递增、完整空结果、跨租户保护、两个未写入交叉桶仍PENDING、新需求仍未满足；独立事务锁住未写入交叉桶时，批量确认不被阻塞。另覆盖过期owner、错误代数、早于冻结观测时间和空版本映射不能确认需求。
