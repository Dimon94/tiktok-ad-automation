# 2026-11-03 按物理接口并行准备领取，末尾短锁公平账本

## 为什么继续修改

44b993c3修正了后台拒绝后退出实时选择、目录锁冲突游标等具体缺陷，但固定30分钟未满足需求仍+3694。同版本后台4→8试验，后台步骤和部分业务完成增加，未满足需求仍+3002、原四长任务无翻页；已按计划恢复实际4和typed4/12，完成验收、释放锁并恢复Jenkins。详见[前版](2026-11-03-dispatch-runnable-fallback.md)与[容量试验](2026-11-03-background-eight-capacity-trial.md)。没有把扩容当作完整解法。

真实PG双连接复现：同租户目录事务准备后续领取时，另一物理接口的实时素材报表返回0；原公平行锁覆盖整个候选和4领取事务，虽然公平余额本来按接口分别存储，不同接口仍串行。新实现中B能在A提交前领取并提交，最终两个接口的余额均保留。

生产家族锁持有者50×0.2秒采样中，活跃SQL一般毫秒级，事务可到1.37秒，存在多次ClientRead；这不支持归因于某一条长SQL，也不能据此声称CPU完全空闲。另一次12轮原协调器有界正常调用提交0领取，大部分家族/游标竞争失败；不能把所有0都归为同一个拒绝。未修改这些被观察函数的决策或返回值。

发送层还复现：outbox每次无条件初始化已存在的DispatchTenantCursor，发送器更新该行时唯一性检查可使生产者200ms超时。改成MVCC确认存在后只在首次初始化INSERT，保留原消息唯一约束和语义核对。生产6秒/60次对应等待样本为0，故仅称已复现隐患，不把它夸大为当前主要等待。

## 完整修改范围

1. 目录、报表、余额领取及idle成本结算统一采用tenant+physical_endpoint事务级try-advisory。只读该接口初始余额，独立shadow cursor不进入ORM Session；选择与成本计算不提前锁整个租户JSON行。
2. 租约、成本和canonical outbox准备完成后，按租户UUID统一顺序短锁已有游标，逐接口比较首次读取的base。相同才合并到最新JSON，并取最大的last_dispatched_at；保留其它接口键。
3. 锁冲突或同键被旧/外部写入者改变时，整个当前家族SAVEPOINT回滚，领取、成本版本、outbox和Redis queued预留均撤销，返回0。不是重读base后覆盖；先前独立家族提交仍保留。
4. 嵌套reservation_transaction成功时把清理责任归并给父事务，最外层COMMIT失败也撤销预留。Redis context位于SAVEPOINT之外，异常先穿出两层后才转成0。
5. idle结算也按接口取锁，只有提交成功才累计结算数量；删除原全租户提前锁入口。原owner/gen/授权、实际平台准入、共享后台容量和成本冻结权重均保持。

无需DDL，schema仍0099；JSON存储格式和任务载荷不变，无新开关、阈值、QPS或资源变化。后台维持4/12。滚动期间旧代码仍可能直接改租户行，最终base CAS专门防止其先提交的同接口余额被覆盖；未把不同键合并误认为同键也天然安全。

## 验证

425项相关真实PG/Redis回归通过、2项可选压测跳过（102.50秒），涵盖整个sync_control、目录份额/读取/事务/大发布/依赖以及outbox。新增测试覆盖：跨接口在对方准备阶段提交、同接口串行、新游标并发初始化、旧写入者先提交导致全部领取回滚、idle在新收据晚到时服从同接口锁、真实PG最外层COMMIT失败释放内层成功预留、发送器更新游标不阻塞生产者。故障分别先复现，再修复；SQL事件只控制有效并发交错，不伪造数据库返回。
