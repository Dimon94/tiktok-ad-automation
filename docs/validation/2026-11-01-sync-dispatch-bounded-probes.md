# 2026-11-01 派发候选扫描与清理边界修复

## 已确认的故障与本轮范围

基于生产 cb51ac01/schema0099 排查。15分钟样本中报表312次HTTP响应、目录235次、回填205次均为平台成功码；报表消息broker等待中位约3ms，但待执行报表约2.86万、目录约3.47万。129次 `sync_cost_ledger FOR UPDATE` 锁超时说明存在内部争用，不能据此认定其是唯一根因或数据库需要升配。

正常派发调用的性能采样（原函数、原准入与事务，无广告写入）：12轮只领取3项。公共池就绪探测调用33次，其中候选发现累计7.107秒；目录资格查询30次累计6.768秒。最初三轮全部因公共池锁被持有而返回0。公平探测在持有公共锁及已结算成本行锁期间发生，放大其他派发与Worker记账的等待。

只读EXPLAIN证明：游标后移后原资格查询虽LIMIT64，但Merge Join从执行引用前缀开始，扫描243013条引用、命中226890个块、333.427ms。单纯重复游标条件或加入OFFSET不能解决，已排除这些候选改法。最终方案先物化64个窄调度头，scope侧也明确同一游标，再按主键检查执行资格；生产等价候选探测为1.549ms、970命中块。两项是查询阶段样本，不是完整系统吞吐倍数。

另一个独立故障：旧plan_continue正文清理15次中6次超时。业务执行正文已有限定ID页，但旧纯唤醒/续点仍在LIMIT前对历史JSON做合同判断。本轮为这两类也复用窄ID页与独立游标；精确正文、期限、所有权及保留期条件保持，未就此删除业务事实。

## 实现与正确性边界

- 就绪探测先读取有界head页，再返回逐项资格；受保护/失效候选也推进扫描游标，到末尾可回绕。不能把不满足执行条件的候选当作可运行。
- 原工作类权重、跨租户公平游标、代数围栏、Redis准入、总执行窗口和Worker并发保持；没有取消公共锁或调用记账。
- 旧唤醒清理游标按任务类型隔离，只有既有事务提交后才持久化；失去游标最多安全重扫。
- 无数据库迁移、运行配置或云资源变更。用户已授权修复并直接上线，按项目现行无DDL快速更新规则，不创建备份或恢复演练。
