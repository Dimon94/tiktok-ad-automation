## 1. 先用正确口径判断是否变快

一个同步任务可以覆盖多个账户、多天和多页数据；一个分页步骤也可能只完成任务的一部分。必须同时看以下指标，不能把“任务/分钟”当作“数据行/分钟”。

| 指标 | 定义与用途 |
| --- | --- |
| 业务完成量 | 原固定任务 ID 集合中，事实已提交且达到各自完成条件的数量；按 account/ad/material/links 分开 |
| 有效写入量 | 提交成功的行数、账户日桶数；重复刷新同一事实也算写入，另统计新增或变化身份，不能混称净新增 |
| API 量 | `sdk_http_started` 为真实尝试；本地准入拒绝不算 API；响应与开始跨窗口允许有差异 |
| 请求效率 | 每千有效变化行的请求数、空页率、重复查询指纹率、缓存命中率、每任务页数分布 |
| 到达率 λ / 服务率 μ | 同类工作每分钟新增与完成量；队列净变化需扣除取消、合并、过期和人工操作；μ 持续大于 λ 才能消化旧积压 |
| 等待与新鲜度 | 最老到期任务年龄、账户日缺口、实时数据延迟 P50/P95；WAITING 要拆为未来计划/限流/依赖/预算/容量 |
| 成本与瓶颈 | Worker 槽秒、阶段耗时、SQL 扫描/返回行、锁等待、连接数、RSS、磁盘与 WAL 增长 |

阶段日志 `timing_semantics=inclusive`：父阶段包含子阶段，不能把 `execute + read + financial_publish` 相加。任务执行成功、任务 COMPLETE、关联完整、图片内容可展示也不是同一个成功条件。

容量近似：同一物理接口可实现的请求率受 `min(平台额度, 本地额度, 可用并发/平均请求占用时间, 下游处理能力)` 约束。并发 4、单请求 2 秒时，该组最多约 2 请求/秒；但一次请求可返回数百行。估算必须扣掉写库、调度和失败重试时间，不能直接承诺清空时刻。

## 3. 配额：不能只问“是不是 3 QPS”

2026-10-31 00:31 北京时间，生产实际基础策略为：兜底 app 10 QPS、logical endpoint 3 QPS；app/tenant/advertiser 在途分别 32/32/4，默认 endpoint 在途 3。窗口 1000 ms，租约 960000 ms。日调用预算参数为 0，不代表平台没有日额度。

- 主要报表和目录的 OFFICIAL_API 覆盖为每物理接口 10 QPS；`reports.material_breakdown`、`ads.get_ads` endpoint 在途 12，其余已覆盖多数读取为 6。`reports.bc` 与 `reports.integrated` 使用同一物理接口桶。
- 已映射读取用物理接口 rate key 替换 app 共用 rate key；不是所有 API 合计 3 QPS，也不是所有接口合计 10 QPS。app/tenant 的在途总预算仍然共享。
- 未覆盖的账户/身份/小程序/图片/部分财务与写操作等，可能受 endpoint 3 QPS 和共享兜底 app 10 QPS 双重限制；bootstrap 入口缺少 channel/rate_group，还要单独核实。
- 空 advertiser 的非账户请求可能共享同一个 advertiser 在途桶。要按业务真实配额域建键，不能用随机账户绕开限制。
- 官方 API 与 MCP 是不同通道；不能拿官方 SDK 的额度直接覆盖 MCP 的约定。

[TikTok 官方频率文档](https://business-api.tiktok.com/gateway/docs/index?doc_id=1740029171730433&identify_key=c0138ffadd90a955c1f0670a56fe348d1d40680b3c89461e09f78ed26785164b)说明 app 额度通常按 endpoint 分别计算，Basic/Advanced/Premium/Ultimate 常规 QPS 分别为 10/20/30/50，另有接口例外以及 QPM/QPD。**本轮没有取得当前 app 实际等级证据，不能据此一律设成 50。** `40100` 是平台响应；本地准入拒绝未发送，平台拒绝已发送。两者都可能使用 `admission_deferred` 错误码，必须按 `admission_source=local/provider` 分别计数。

配额治理顺序：建立“逻辑操作 → 物理 endpoint → 实际 app 等级/例外 → QPS/QPM/QPD → 在途预算”清单；所有 SDK 发送入口共用；校验跨角色策略摘要；再按一个接口逐级提高。并发是本机容量控制，不能机械等于 QPS。上传有独立临时资源容量，不能给它沿用读取的高在途数。

混合版本上线必须评估 Redis key 变化：新旧 Worker 若各用一套桶，过渡期间会重复获得额度；新 QPM/QPD 桶空状态也不能当作本窗口完全没调用过。配额修改要有单窗口有效范围与回滚方案。

## 5. 千万级容量：现在就要治理

本库已不是小数据：10/31 00:31 元数据估算 `ad_object` 2693 万、`ad_material_reference` 3504 万、`pending_dispatch` 1459 万；数据库约 110.86 GiB。估算不是精确 COUNT，不代表活跃广告数量。

目录对象主键为租户/账户/类型/remote_id；素材引用按使用身份唯一。发布是同身份 UPSERT，**不是每次完整复制一版**。旧使用身份为历史消耗归属保留；按全表最大 version 清旧行会破坏正确性。`current_ad_materials()` 仍会取一个广告的 complete 历史身份并在 Python 选最新，需测单广告长尾后再设计当前投影/历史归档。

扩展应分别处理：

1. 日事实：已有时间分区，确认查询带日期且分区裁剪生效；预建后续分区，避免发布事务临时 ATTACH 时持强锁。
2. 活跃调度表：以到期/状态/租约索引支持小候选领取；历史任务不参加活跃全排序。
3. 控制流水与暂存：终结数据有明确保留期和引用检查；outbox 的幂等墓碑可与大 payload 分离，先定合同再删。
4. 目录与历史身份：当前操作查询与历史核算查询分别优化，保留历史可追溯性；不是仅凭行数就拆表。
5. 大单任务：校验页链与末页发布的内存/时间成本要有上界；跨页完整性必须保留，不能用去掉校验换速度。

若真的首次拉取 1000 万结果行，按 100 行/页至少需要 10 万页，按 1000 行/页至少 1 万页；这是理想页数下界，不含空页、重试和关联。日常同步应随活跃变化量增长，而不是随全库历史大小线性增长。

[PostgreSQL 官方分区说明](https://www.postgresql.org/docs/current/ddl-partitioning.html)强调分区裁剪与维护收益，也说明附加分区的锁行为；分区不是自动加速所有查询。[Celery 优化说明](https://docs.celeryq.dev/en/latest/userguide/optimizing.html)区分预取、长短任务路由与实际吞吐；扩大候补队列不会凭空增加进程能力。

## 6. 标准排查与验收流程

1. 冻结证据：部署 SHA、迁移版本、策略摘要、Worker 副本/并发、队列映射、数据库连接预算、时间与时区。区分已上线、已提交未上线、未提交 WIP。
2. 选固定 ID 队列，分别记录新增工作与固定队列完成；至少覆盖 3×15 分钟，再观察 24 小时及账户跨日、30 分钟余额周期。短窗口只报实测，不报持续 SLA。
3. 查准入日志：分别统计本地 rate/inflight 与平台 40100、Retry-After。按物理接口、租户和任务类分组；不要把所有 WAITING 当成重复任务。
4. 看 Worker 槽秒：HTTP、发布、补位分别占多少；broker wait 高不直接证明队列路由错，满并发也不直接证明 CPU 满载。
5. 查 DB：先统计视图、锁持有者、代表性参数执行计划，再做定向查询；事务长不等于一直阻塞别人。冷/热缓存与 generic/custom plan 都要验证。
6. 单项改动后比较：有效变化行/请求、μ−λ、最老任务年龄、实时 P95、40100、SQL/槽秒成本。若只提升一个 lane 并使另一 lane 失速，不算整体优化完成。
7. 回滚触发事先写清：覆盖/金额错误立即停止扩容；平台拒绝率、实时延迟或 DB 等待持续恶化就退回本次具体参数/版本。已有业务待处理任务保持可恢复，不能靠清空积压制造成绩。

只读统计示例（在确认正确生产目标后执行；连接和凭据不入文档）：

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '4s';
SET LOCAL lock_timeout = '300ms';
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
WHERE relname IN ('ad_object','ad_material_reference','pending_dispatch',
                  'report_sync_job','report_sync_page','ad_directory_run');
ROLLBACK;
```

只用 `EXPLAIN` 先看计划；`EXPLAIN ANALYZE` 会执行 SQL，需选择有索引的小范围读查询并限时。不要对千万级表直接无条件 COUNT，或为了观察安装扩展、执行清理。统计快照只给线索，不替代持续 IOPS/CPU/内存监控。

后续每轮记录固定模板：**问题证据 → 可证伪假设 → 最小变更 → 正确性回归 → 生产前后同口径窗口 → 余留问题与下一项**。不再用“提交了优化”替代“业务结果持续改善”。

## 9. 报表发布也要检查逐桶往返

[2026-11-01批量发布记录](../validation/2026-11-01-batch-report-publication.md)补充了一个容易遗漏的放大点：事实已批量写入，但每个账户日期仍各自查询状态、确认需求并flush，导致客户端数据库执行调用随桶数增长。现按500桶批量预读与确认，保持同一业务事务，不减少本轮处理账户。

- 批量需求确认必须使用实际写入的`(advertiser_id, bucket_key) -> publication_version`，不能将账户集合和日期集合交叉组合；被新水位保护的空洞不能误确认。
- 统计客户端execute/executemany批次数时，同时注明服务器仍可能执行多条语句；局部调用减少比例不是整体吞吐倍数。比较生产耗时须按报表类型和相同桶数分组，避免任务大小变化造成误判。
- `publish_projection`单独计量广告报表查询汇总重建，仍包含在父阶段`financial_publish`内，不与父阶段相加。阶段返回不代表提交，吞吐只统计`job_commit_confirmed`且`job_commit_result=COMPLETE`的结果。
- 公共调度锁高占用可能来自连续的短事务，而非单个长事务。应记录持锁事务年龄和执行路径，再区分候选扫描、派发、远端读取及本地发布的槽占用，不能直接增加并发。


## 10. 余额半小时重复与调度历史扫描（2026-11-02）

不要只验证刚发布的15分钟吞吐。周期计划在上一周期未完成时继续新建批次，会使执行引用长期膨胀，即使真实需求表已经去重，调度仍会越来越慢。本次同账户最多62份余额批次，候选查询展开25万行才选1条；只看Worker在线和全局QPS无法发现。

周期tick采用单飞语义：未完成账户继续原执行，不重置页码、不抬高正在执行的冻结revision，不锁无新增缺口的所有账户。完成后的下一周期重新请求新鲜度；新账户或owner变化单独建批。旧重复仅在同租户、actor、冻结路由、owner下有完整更新执行承接时取消，不能将取消算作同步成功。

已授权清理时，在正确生产环境使用 `scripts/compact-balance-runs.py`；默认预演回滚，`--apply`提交，默认最多256候选、60秒；每批独立事务、锁冲突跳过。保留终态记录、成本收据与原始事实，正常outbox围栏拒绝旧消息。不得把缺失余额补0，也不直接删除需求/执行表。

查询验收同时看空队列和深积压：一条空成本结算不应扫十几万条历史收据。现有partial index前缀为tenant/endpoint/id，按endpoint/id取脏收据；余额先选择执行再验证owner和账户头。生产只读计划25.5ms与0.14ms不等于整体吞吐提升倍数。继续统计真实需求减少、自然完成、周期新增与取消重复，至少观察两个半小时周期；日志窗口需一致，日终回刷峰值单独验收。

详细证据、发布版本和剩余问题见[本轮验收](../validation/2026-11-02-balance-dispatch-amplification.md)。

报表存量覆盖清理使用 `scripts/compact-covered-report-runs.py`，默认预演，`--apply`逐任务提交；仅QUEUED/WAITING且无有效租约，全部引用有真实同owner发布证据时取消。保留运行中任务及后续新需求；需求水位计数满足只是候选，不能取代发布revision/观察时间/版本证明。工具不是新的周期调度器。见[清理验收](../validation/2026-11-02-covered-task-compaction.md)。


## 2026-11-02 调度、发布和查询汇总的共同验收

- 独立实时池不应先抢公共后台池锁。仅实际后台准入保留共享容量锁；家族窗口锁、租户cursor和费用账仍保留。多家族并行后cursor必须SKIP LOCKED，防止锁顺序互等。
- 到期租户发现使用租户驱动的相关EXISTS；目录必须限定PENDING引用以命中部分索引。生产同口径查询88.1→1.84ms，只代表该查询，不能换算全系统倍率。
- 检查周期任务的过期丢弃日志。5秒汇总tick放入忙碌的单进程发布队列会在执行前过期，使远端同步越快、前端投影越落后。当前汇总路由为ads-reporting；逐桶SKIP LOCKED和source_revision围栏保持。
- 总目录窗口满时先分解publish_ready：40/40都已读完说明堵在本地发布，继续加读取并发或TikTok额度没有用。当前ACK publisher清单4进程，原1C/2Gi限制，数据库池每子进程2+1；增长前后核验RSS、队列、锁等待、连接预算和实际完成量。
- 动态Celery pool_grow的stats max-concurrency可能保留启动值；验证processes实际数量。试验成功后必须更新受版本控制的清单并回读新Pod，不能依赖重启后丢失的临时状态。
- 同时记录报表/目录待执行数、未满足需求和查询脏桶；步骤/分钟不是完整账户/分钟，取消旧任务不算同步吞吐。部署混合版本窗口单独标识，不与稳定窗口拼接计算倍率。


当前页补全也必须检查真实执行计划：`tenant + advertiser_id IN(...) + video ANY(...)` 即使已有视频索引，也可能选择按账户扫描全目录。可用当前页身份驱动相关索引探测，保留tenant范围并在外层SQL执行授权账户过滤；不能靠丢弃关联、截断位置数或只返回一个账户加速。发布前在同一数据库快照逐字段比较结果，分开记录补全SQL与候选排序/快照构建时间。高随机I/O成本的计划回归须包含大账户集合，避免相关子查询把一个错误全扫放大为每个素材一次全扫。


本轮最终实测与剩余边界：今天/7天的生产服务查询分别为：系列4.01/16.02秒、广告1.40/17.14秒、素材4.52/22.70秒。素材对照35.07/56.91秒明显改善；7天范围仍非秒级，剩余主要在查询快照构建，本轮没有宣称所有页面性能已完成。服务查询是正常查询快照路径，不是浏览器端到端计时；持续同步期间成员数变化，SQL字段等价另用REPEATABLE READ验证。 同步观察必须同时列新建量、真实缺口、发布成功和锁重试。补链唯一键错误已用生产同类数据复现并修复，不能以扩大配额掩盖事务回滚。当前每领取仍有较多SQL往返，下一轮先按事务和函数分解重复查询，避免因某个8ms候选查询被采样到就再改写排序。


租户游标跳锁须先于初始化写入：INSERT ON CONFLICT DO NOTHING也可能等待另一事务UPDATE产生的唯一索引项，不能只在后面的SELECT加SKIP LOCKED。测试必须包含另一连接实际UPDATE并flush的情况，同时验证首次初始化竞争和旧游标不再执行INSERT。每批最多4步、批间提交释放锁，默认Worker补位同样使用4秒SQL总预算。详见[实测](../validation/2026-11-02-dispatch-batching.md)。


统计口径必须分开：同步任务是账户/类型/日期或对象范围，执行步骤是一次读取或发布推进，HTTP请求是实际平台尝试，数据记录是处理或更新的行。一个任务可有多步、多页和很多行；未满足需求按scope/bucket计数，同样不是原始记录数。报表必须同时展示完整任务完成、需求净变化、周期新增波峰，以及人工清理/真实覆盖终止，禁止把接口成功数或删任务数当成同步吞吐。

### 空闲执行池与公平份额

后台物理池的公平轮次不能使空闲Worker等待另一个家族主动来申请。判断时同时记录实际typed占用、capacity、prefetch、准入拒绝原因及候选所属类；仅看队列长度或Worker进程数不足以定位。低于capacity时可借用空槽，按实际获派类扣除份额保留债务；达到capacity后按公平赢家排队，总占位仍不超过capacity+prefetch。平台app/tenant/account/endpoint准入独立保留。回归必须同时证明空槽可借、拥塞仍公平、总上限不越界。

普通及独立实时/发布候选均用scope游标有界扫页，两种模式分开记录位置；页间轮转、页内按真实服务年龄选候选。游标只记录发现位置，事务回滚后仍能越过无资格前缀。取得候选后，短锁内重新复验租户、owner、generation、真实状态与due，不能把缓存的发现结果当作执行授权。监控应记录页大小、扫描位置推进及旧任务实际页数，不能只记录LIMIT返回一行。64头是候选发现页，不是每轮仅允许同步64账户；循环继续发现，真实并发与费用窗口保持。

### 需求放大与续点饥饿的联合验收（2026-11-03）

状态轮询不应因平台返回素材信息不全就自动展开全部素材详情；素材关联缺口走明确identity需求。核对新子任务来源时包含已成功的子任务，不能只看仍待办样本；子任务可能继承父created_at，目录新增量用request_sequence边界统计。取消可选任务单列，不改变缺口满足水位。

material_links无领取、无暂存页、无分页续点且只等目录证据时，同一账户日期的新需求可承接到原任务；必须加锁复验并清旧observed_at，下一代建立真实观察。普通WAITING、在途快照、金额报表和范围扩张不能采用此规则。依赖完成后仍须沿正常确认路径发布，不能仅因复用任务就提高satisfied_revision。

公平调度不能把NULL last_dispatched_at永久排在所有旧续点之前。新头用真实oldest_pending_at参加轮转，已服务头用last_dispatched_at，缺省以执行created_at兜底；既验证老续点能拿到一步，也验证服务后会让回新任务。测试只覆盖空队列、一个任务或静态存量时发现不了持续新到达造成的饥饿。

复核后延期/退休也必须更新头的调度服务时间，否则同头多个周期副本会占完每轮复核次数，遮住其它接口的独立池。last_dispatched_at用于内部服务轮转；真正发消息和HTTP分别看outbox/dispatch及SDK记录。零HTTP的复核不扣平台费用，不增加执行代数或满足水位。复现必须包含同头多份副本与另一接口可执行工作，不能只测单份延期正确。

固定版本至少覆盖一个15分钟热刷周期，另核对半小时/三小时/日终周期；15分钟不能宣称已经覆盖三小时目录校准。同时保留固定老任务的页码/代数、周期新增量、真正COMPLETE、覆盖取消、未满足桶和同口径待办。一个事实类型下降不能掩盖身份链路不动；短窗下降后重启部署再采短窗也不能证明稳定净消化。


## 2026-11-03 拒绝路径也必须释放本次分配锁

候选/额度可运行而Worker有空槽时，先关联同刻active、含预取typed占位、broker深度、due outbox年龄和候选readiness，再讨论扩容。事务级锁在函数返回False时不会自动释放；用保存点撤销失败尝试的新锁，已成功分配的锁仍保留到真实租约提交。发现游标应独立于失败SQL事务，否则修锁又可能重扫同一阻塞前缀。重试预算须按原因和租户隔离，不能让一个租户锁冲突为另一租户维护增加次数。实际计时和回归边界见[本轮验收](../validation/2026-11-03-sync-dispatch-lock-lifecycle.md)，未将40–300ms持锁夸大为分钟级长锁。


## 广告接口增量能力的官方核验（2026-11-04，尚未实施）

官方[Get ads](https://business-api.tiktok.com/portal/docs?id=1735735588640770)渲染文档已确认`filtering.modified_after`可按UTC修改时间筛选，格式`YYYY-MM-DD HH:MM:SS`；SDK的[Regular过滤模型](https://github.com/tiktok/tiktok-business-api-sdk/blob/main/python_sdk/docs/FilteringAdGet.md)和[Smart+过滤模型](https://github.com/tiktok/tiktok-business-api-sdk/blob/main/python_sdk/docs/FilteringSmartPlusAdGet.md)均包含该字段。SDK字段存在不能替代各API完整语义验证。当前目录同步尚未使用它，不能继续笼统声称TikTok没有广告增量筛选能力。

它不等同于SPI/RDS完整变更流，也不允许以增量结果冒称已补全历史素材身份。实施前须区分已有完整基线后的变更更新与仍缺旧事实的冷启动全扫；确认删除查询、时间精度、重叠窗口、并发分页、权限/owner变更、全量校准和独立覆盖水位。官方文档说明删除广告默认不返回，须显式查询相应删除状态；因此不能把未返回当删除。此处仅记录已核验能力与实现前提，当前生产查询/水位未变。
