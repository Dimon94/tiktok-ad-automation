# 余额周期重复与公共调度扫描修复

## 证据与边界

生产 7b0a2d7f，2026-11-02：248 个 ACTIVE 余额批次，404147 个剩余账户引用，同一账户最多 60 批。选一个余额执行展开 252668 行、约 2.19 秒；空成本结算扫描 145365 条历史收据、134ms。这些查询处于公共后台调度锁内。上一轮发布批量写入提速确实存在，但十五分钟验收没有覆盖跨周期累积，不能视为整体问题已解决。

## 实施顺序

1. 周期余额刷新采用与报表 pending 覆盖相同的单飞语义：同租户、操作者、冻结路由、owner 有效的 ACTIVE 批次中仍未完成的账户不重复建执行；新账户和 owner 变化创建独立执行。周期 tick 不是新用户强制刷新，不修改既有执行页码、冻结 revision 或新鲜度水位。完成后的下一周期仍会创建真正的新需求。
2. 历史重复批次仅在更新批次完整承接剩余账户、冻结 revision 与请求时间，且旧批次无有效执行租约时取消。保持有效在途执行、原始余额事实、未满足需求、成本收据和消息围栏。取消必须记为 superseded，不记成功；分批短事务，保留审计结果。范围不同不得混并。
3. 余额派发先挑一个到期执行，再验证整批 owner 并选其到期头；去掉 scope×run 展开后排序。保留租户公平、后台窗口、配额、消息原子性。余额类内部按执行创建时间 FIFO；跳过锁定与无效批次。
4. 成本结算按现有 partial index 的 endpoint/id 顺序取脏收据，避免 ORDER BY id 诱导扫描历史主键。端点间成本独立，不改变收费、未知保守保留或结算版本。
5. 真实 PostgreSQL/Redis 测试：跨多个半小时、账户新增/完成/owner 变化；旧批次安全合并与在途保护；深度重复及历史收据的查询计划；消息与成本围栏回归。
6. 无 DDL、配额、并发、开关变更。独立工作树验证，合并公司 main，精确 SHA 正常滚动发布，沿用用户免备份/免恢复演练/免全量排空授权。上线核验至少两个半小时周期的新增、完成、需求年龄、调度耗时和重复增长；不能将取消数量算同步吞吐。

## 验收与后续

先消除重复增长与锁内大扫描，再测实际供给/处理速率。每天历史回刷仍会输入新工作，不能为了下降数字跳过历史覆盖；若恢复供给后净新增仍大于完成，记录分类净流量，再单独设计回刷频率及预算。无充分证据不继续加云资源、不承诺积压清空时刻。
